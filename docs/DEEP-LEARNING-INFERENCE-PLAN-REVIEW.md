# DEEP-LEARNING-INFERENCE-PLAN 开工评审意见

评审日期：2026-10-09
评审对象：`docs\DEEP-LEARNING-INFERENCE-PLAN.md`
评审方式：与当前代码核对（`VisionFlow.Tools\Tools\DeepLearningTools.cs`、`VisionFlow.Tests\DeepLearningInferenceToolTests.cs`、`ToolboxRegistry` / `BuiltinToolIdentities` 的登记方式、前几条线的“先探测后实现”经验）并结合本机 HALCON 22.11 实测结论。
评审结论：**可以进入方案阶段评审，但暂不建议直接开写分类 / 检测 / 分割代码。必须先做一轮深度学习结果结构探测，再按“检测 → 分类 → 分割”的顺序落地。当前第一阶段统一运行时保留，方向正确。**

## 1. 总体评价

- 方案拆分正确：分类、检测、分割输出差异大，继续堆到 `DeepLearningInferenceTool` 一个类里会迅速失控，拆 3 个专用工具是对的。
- 当前基础可复用：第一阶段已经把 `.hdl` 加载、类型检查、设备策略、batch 和公共元数据稳定下来，这部分不应推倒重来。
- 风险识别到位：真正的技术不确定性在 HALCON 深度学习结果 dict 的 .NET 落点，而不是工具箱登记、序列化或 WPF 路由。
- 推荐顺序合理：检测已有 `detect_pills.hdl` 真实模型验证基础，最适合作为第二阶段第一枪。

## 2. 已核实的正向前提

## 3. P1：动工前必须处理

### P1-1 先补深度学习结果结构探测节（硬性）

当前计划的最大缺口是：虽然已经知道模型“能加载”，但还不知道分类 / 检测 / 分割结果在 HalconDotNet 里究竟以什么结构返回。必须先做探测，并把结论补进计划。

最低探测清单：

| 接口 | 要确认什么 |
|---|---|
| `ApplyDlModel` | 参数签名、返回值类型、dict 顶层键名 |
| `ApplyDlClassifier` | 是否应只用于分类模型，和 `ApplyDlModel` 的差异 |
| 分类模型返回 | 类别名、类别 ID、分数、TopK 的读取方式 |
| 检测模型返回 | 框坐标字段、类别字段、分数字段、目标顺序 |
| 分割模型返回 | 掩膜 / 类别图 / 区域的真实结构 |
| ROI 参与方式 | `reduce_domain` 后深度学习结果坐标是否仍是原图坐标 |
| Batch 语义 | `BatchSize > 1` 在单图 / 多图输入下的实际行为 |

没有这轮探测，后面的接口设计仍然只是“猜测型设计”，不适合直接编码。

### P1-2 公共运行时与专用结果层的边界要再钉死（硬性）

第二阶段写代码前，必须明确以下边界：

- `DeepLearningInferenceTool` 继续只负责“模型已就绪 + 公共元数据”，不追加分类框、检测框、掩膜等业务输出。
- DL-01 / DL-02 / DL-03 可以共享内部帮助类或基类，但对外必须是独立工具和独立持久化 ID。
- 专用工具若需要复用模型缓存，必须复用“同一份缓存键规则”，避免一边预热 CPU、一边运行 GPU 导致结果错乱。

否则实现时很容易又回到“先在 `dl-infer` 上多加几个输出”的路径，后续不可维护。

### P1-3 ROI 语义必须先定，不要边写边猜

当前计划已经提到 ROI，但没有定死语义。深度学习这条线里 ROI 不是小问题，直接影响检测框和分割区域坐标。

写代码前必须在计划里明确：

- ROI 是裁图后推理，还是仅作为兴趣域提示。
- 若裁图推理，检测框 / 掩膜 / 区域回写到原图时如何加偏移。
- 若存在定位矩阵跟随，是否允许与 ROI 同时使用，还是分版本实现。

建议第一版采用最简单且可验证的策略：`reduce_domain` 或裁剪后推理，结果统一映射回原图坐标；矩阵跟随不并入第一版。

### P1-4 第一版只做单图推理，不做“真批量输入”

计划里保留了 `BatchSize`，这是对的，但第一版不要同时引入图像数组输入。原因：

- 当前流程系统的单图语义已经成熟，图像数组会把输入、输出、日志和错误处理都放大一倍。
- 真实业务里先把单图闭环跑通，比抢做批量更重要。
- `BatchSize` 可以先作为模型运行参数保留；等单图路径稳定，再决定是否支持图像数组输入。

这条边界建议写进计划正文，避免实现期范围膨胀。

## 4. P2：开发中落实

1. **工具命名与 ID**：建议直接使用 `dl-classify` / `dl-detect` / `dl-segment`，与 `dl-infer` 并列，短而稳定。
2. **输出结构对齐既有工具**：检测与分割尽量复用现有 `Region` / `XLD` / 数组变量消费方式，不新造只在深度学习线可用的特殊类型。
3. **编辑器先做最小闭环**：第一版以“加载图像、执行测试、看叠加结果”为目标，不提前做复杂标注或批量浏览器。
4. **错误信息中文化**：HALCON 深度学习错误必须转成明确中文，尤其是模型类型不匹配、设备不可用、结果字段缺失三类。
5. **真实官方模型门禁测试**：每个专用工具至少固定一个官方模型 + 示例图的门禁用例，不只做非 HALCON 假数据测试。

## 5. P3：文档维护

1. `docs\DEEP-LEARNING-INFERENCE-PLAN.md` 在探测后补“算子探测结论”节，格式沿用前几条线。
2. `README.md` 暂不更新“已实现分类 / 检测 / 分割”，直到真实功能落地为止；当前保留“第一阶段公共运行时”描述是正确的。
3. 每做完一个任务型工具，再补对应实现与验收记录，不要提前把计划写成完成态。

## 6. 推荐顺序确认

- **先做探测**：这是硬前置，不可跳。
- **第一批做 DL-02 检测**：现有官方模型验证基础最好，产出也最容易肉眼验收。
- **第二批做 DL-01 分类**：结构简单，适合在检测之后快速补齐。
- **第三批做 DL-03 分割**：输出最复杂，放最后最稳。

## 7. 结论

- 当前阶段最正确的动作不是继续写代码，而是先把计划和探测补完整。
- 统一运行时第一阶段保留，作为三类专用工具的底座继续复用。
- 评审通过后，下一步应先做 HALCON 深度学习结果结构探测，再进入 DL-02 检测编码。
