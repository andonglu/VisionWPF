# VisionFlow 问题清单与修改建议

评估日期：2026-09-15
评估范围：当前工作区实现，包括评估时尚未提交的修改。
文档状态：首次评估的问题与验收依据；当前整改结果见 `docs\REVIEW-FIX-PROGRESS.md`，下文的初始现状不代表最新代码。

范围调整（2026-09-15）：按使用方要求，不提供撤销/重做，也不再将其列为待办或验收缺口。保留参数取消、脏标记、未保存提示和保存失败保护。

## 1. 评估原则

当前项目已经具备视觉工具编排、参数配置、运行调试和流程持久化的基本闭环。建议保留现有树式流程、独立运行接口、元数据驱动参数编辑以及专用视觉编辑器的主线，通过局部改进提高可靠性，不建议推倒重来。

本清单区分三类结论：

- **已确认问题**：当前实现存在可以明确说明的行为不一致或功能缺口。
- **设计风险**：边界或协议不明确，存在出错条件，但不等于已经证明现场故障。
- **成熟度缺口**：仍需通过工程能力或实际数据补足，不能仅凭源码判断效果达标。

相机采集、PLC/IO/运动控制、MES、生产调度和完整配方管理属于上层设备程序，不列为本项目缺陷。实际精度、重复性、误检漏检率和节拍没有现场数据支撑，不作达标结论。

## 2. 优先级总览

P0：优先保证执行与结果正确性。
P1：完善长期运行、上层集成和兼容性。
P2：改善维护成本和编辑体验。

| VF-03 | P0 | 定位矩阵失效后自动退回固定位置测量 | 已确认行为，存在结果正确性风险 |

## 3. 问题详情与修改建议

### VF-01：统一引用解析、类型判断与作用域规则

**现状与影响**

运行时通过 `VariableReference` 解析引用，校验器却主要通过与候选路径进行精确匹配判断合法性，两者不是同一套语义：

- `Source.Values[0]` 等数组元素引用可以被运行时求值，但可能被声明级校验拒绝。
- 分析 Else 内部节点时，上游收集会经过 If 分支，导致 Else 可以错误地通过对 If 私有输出的引用校验；真正执行 Else 时，该变量不存在。
- 对数组索引、对象成员、集合类型和嵌套控制结构的支持，不能仅依赖下拉框已经展开了哪些候选项。

**关键位置**

`VisionFlow.Base\Variables\VariableReference.cs`
`VisionFlow.Base\Editing\RefCandidates.cs`：`CollectUpstream`、`CollectSubtreeOutputs`
`VisionFlow.Base\Validation\FlowValidator.cs`：`ValidateReference`、`ValidateBranchOutputOperand`

**修改建议**

1. 复用引用解析结果，按“输出声明 → 数组索引 → 成员路径”逐段推导类型，不以候选字符串列表代替引用语义。
2. 将校验和候选生成建立在共享的作用域规则上；If 与 Else 的私有输出不得互相可见。
3. 分支外默认只暴露显式公共输出；嵌套分支同样遵循该规则。
4. 明确循环零次执行时的输出可用性，以及最内层 `Loop.*` 的解析规则。
5. 区分静态可判断错误与运行期错误：例如不存在的成员可以提前报错，数组实际长度不足仍需运行期明确报错。

**验收要点**

合法数组索引和成员链不会被误拒绝；跨互斥分支引用会被阻止；嵌套分支和循环作用域一致；类型不符、缺失变量和索引越界均有明确错误信息。

### VF-02：隔离运行状态与编辑状态

**现状与影响**

WPF 将 `_model.Root` 直接交给后台运行。`SetRunningState` 主要修改停止按钮和鼠标状态，没有统一禁止节点增删移动、参数修改、流程切换或换图。

运行时和编辑器因此可能访问同一个可变节点集合、工具实例和输入图像。换图操作还会释放旧的 `_inputImage`，而当前运行上下文可能仍然引用该对象。

**关键位置**

`VisionFlow.WpfApp\MainWindow.xaml.cs`：`RunFlowAsync`、`SetRunningState`、`OpenImage_Click`、节点编辑与流程切换入口
`VisionFlow.Base\Engine\FlowEngine.cs`：`RunAsync`

**修改建议**

1. 当前阶段先锁定运行期间的结构编辑、参数修改、工具预览、流程切换和换图操作，保留停止及只读查看能力。
2. 在统一的运行会话状态中控制相关命令，避免只禁用某个按钮而遗漏其他入口。
3. 请求取消后，必须等后台执行实际结束，再恢复编辑能力或释放输入资源。
4. 确实需要边运行边编辑时，再引入独立的流程配置快照、工具实例和输入资源管理；不能只复制节点列表而继续共享工具对象。
5. 明确取消是协作式的：当前同步 HALCON 算子未返回前，取消请求不等于已经停止。

**验收要点**

运行期间无法改变本次执行使用的配置和输入；停止请求后不会提前恢复可写操作；正常结束、取消和异常结束都能恢复正确的界面状态。

### VF-03：定位配置失效时不得隐式固定位置测量

**现状与影响**

`FollowMeasureToolBase.GetMatrixOrNull`、`GetMatrices` 在矩阵引用解析失败或类型错误时，记录警告并退回固定位置测量；空矩阵集合也可能被转成固定位置测量。

这可能产生“工具执行成功，但测量位置不正确”的结果。日志中的警告不足以保证上层不会将结果用于判定。

**关键位置**

`VisionFlow.Tools\Tools\MeasureTools.cs`：`FollowMeasureToolBase`，尤其是矩阵解析方法

**修改建议**

1. 区分“未配置定位跟随”和“已配置定位跟随但解析失败”。
2. 未配置时允许固定位置测量；已配置但引用不存在、类型错误或矩阵无效时，明确返回失败。
3. 空矩阵集合按明确的业务语义返回空结果或失败，不应自动解释为固定位置。
4. 如果确需预览降级，将其作为显式预览选项，不复用为默认生产执行行为。
5. 错误信息应包含节点、引用路径和失败原因，便于上层定位。

**验收要点**

未配置矩阵时原有固定测量仍可使用；配置错误时不会输出看似正常的固定位置测量结果；单矩阵、多矩阵和空集合行为都有明确约定。

### VF-04：建立 HALCON 对象与模型生命周期协议

**现状与影响**

不少工具已经释放中间对象，但 `HalconImage`、`HalconRegion`、`HalconXld` 仅包装底层对象，`FlowContext` 没有统一资源释放协议。同一底层对象还可能被多个变量或预览界面同时引用。

这些现象不直接证明必然泄漏，但使持续运行、输出覆盖、反复预览和异常退出时的资源行为难以保证。

部分模板工具每次执行都会重新加载或反序列化模型，然后清理句柄。这是性能评估点，不应在没有数据时直接认定为瓶颈。

**关键位置**

`VisionFlow.Base\Variables\HalconTypes.cs`
`VisionFlow.Base\Core\FlowContext.cs`
`VisionFlow.Tools\Tools\HalconTools.cs`
`VisionFlow.Tools\Tools\ShapeModelSerialization.cs`

**修改建议**

1. 明确哪些资源属于调用方借用输入、哪些属于本次运行、哪些属于工具或模型会话。
2. 为一次运行及其结果定义可释放的资源边界；结果仍在展示时，不得提前释放。
3. 处理输出别名和共享对象，避免简单地遍历变量逐个 `Dispose` 造成重复释放。
4. 覆盖成功、失败、取消、替换结果和关闭编辑器等生命周期路径。
5. 测量模型加载耗时后，再决定是否按运行实例缓存；缓存必须同时具有失效、释放和并发隔离策略。

**验收要点**

长时间重复运行与预览的资源占用符合预期；调用方输入不会被错误释放；旧结果替换后资源能够回收；共享对象不会重复释放；模型更新后不会继续使用旧缓存。

### VF-05：完善外部输入与运行结果契约

**现状与影响**

`FlowContext` 能接受任意外部变量，但校验器只内置 `Input.Image`。例如上层注入 `Input.PartId` 后，运行时可以使用，声明级校验却无法识别。

`FlowRunResult` 直接持有上下文，`NodeReports` 是上下文列表的只读视图而非快照。复用同一个上下文再次运行，会追加日志和报告，先前结果看到的报告数量也会改变。变量是否允许跨次保留，同样没有明确的调用约束。

**关键位置**

`VisionFlow.Base\Validation\FlowValidator.cs`：`AddInputImage`
`VisionFlow.Base\Core\FlowContext.cs`
`VisionFlow.Base\Engine\FlowEngine.cs`：`FlowRunResult`、`Run`
`VisionFlow.Base\Runtime\IVisionFlowRuntime.cs`

**修改建议**

1. 增加可声明的外部输入描述，包括名称、类型、必填性及必要的默认值规则，并提供给编辑器和校验器。
2. 保留 `Input.Image` 的便捷默认行为，同时允许上层声明额外图像、编号、阈值或坐标等输入。
3. 默认每次执行创建独立上下文；如果支持上下文复用，应显式定义清理和保留规则。
4. 结构化日志、节点报告等结果元数据应形成稳定快照；HALCON 结果对象则结合资源协议约定有效期，不要求盲目深复制。
5. 明确“流程执行成功”与“视觉业务判定 OK”的区别，不将 `NodeStatus.Success` 自动当作产品合格。

**验收要点**

自定义外部输入能够被选择、校验和执行；缺失必填输入有明确错误；连续运行不会污染前一次结果；执行状态与业务输出可以分别读取。

### VF-06：为流程文件增加版本与兼容机制

**现状与影响**

工具持久化依赖 `AssemblyQualifiedName`，加载时通过 `Type.GetType` 还原类型。节点 DTO 没有明确的文件版本，工具参数仅保存指定的简单类型。

简单类型白名单本身是合理约束，但新增复杂参数、类改名或程序集拆分时，如果缺少兼容策略，容易造成旧流程无法加载或参数未被保存。

**关键位置**

`VisionFlow.Base\Runtime\FlowSerializer.cs`：`ToToolDto`、`FromToolDto`、`SerializableProperties`、`NodeDto`
`VisionFlow.Base\Core\ToolboxToolAttribute.cs`

**修改建议**

1. 引入稳定工具标识，优先复用或扩展已有工具注册 ID，不再仅以 CLR 类型名作为持久化身份。
2. 增加流程文件版本；工具参数结构变化较大时，再增加工具参数版本。
3. 为已发布格式提供显式迁移路径，并保留现有 `TypeName` 文件的兼容读取能力。
4. 遇到未知工具、未知版本或不支持的参数时给出明确提示，避免静默丢失配置。
5. 保留当前模型字节内嵌能力，同时明确外部图像、模型和标定文件路径的迁移规则。

**验收要点**

现有示例和旧版文件仍可读取；工具重命名后可通过稳定 ID 或迁移映射恢复；不支持的版本明确失败；保存再加载后关键参数与模型数据保持一致。

### VF-07：打通 WPF 插件编辑器的注册与打开链路

**现状与影响**

插件加载器通过 `ToolEditPageRegistry` 注册编辑器，但 WPF 主窗口主要采用内置工具类型判断打开窗口，最后回退到通用编辑器。

因此，插件工具进入工具箱，不代表插件声明的专用编辑器会被 WPF 使用。

**关键位置**

`VisionFlow.EditorCore\Editing\VisionFlowPluginLoader.cs`：`RegisterFromAssembly`
`VisionFlow.ToolEditors\Ui\ToolEditPageRegistry.cs`
`VisionFlow.WpfApp\MainWindow.xaml.cs`：`OpenToolEditor`、`IsVisualPreviewTool`

**修改建议**

1. 为 WPF 提供明确的工具编辑器注册与查找入口，主窗口通过注册表分发。
2. 区分工具执行注册与平台相关的编辑器注册，避免两者在公共接口中互相绑定。
3. 保留无专用编辑器时的通用编辑器回退，但对注册失败和不兼容情况提供可见诊断。
4. 明确内置编辑器、插件编辑器、重复注册及覆盖行为的优先级。
5. 兼容现有 WinForms 编辑器，不要求一次性重写所有插件页面。

**验收要点**

插件 DLL 被发现后，工具可添加、参数可保存、专用编辑器可实际打开；无专用页面时正常回退；注册冲突有明确说明。

### VF-08：按职责拆分 UI，而不是机械迁移到 ViewModel

**现状与影响**

`MainWindow.xaml.cs` 同时负责工具箱、流程树、参数面板、文件读写、运行控制、结果显示和工具编辑器路由。

`FlowEditModel` 本身具有 UI 无关性，但 `VisionFlow.EditorCore.csproj` 引用了 WinForms 工具编辑器并启用 `UseWindowsForms`，逻辑分层与项目依赖边界尚未完全一致。

**修改建议**

1. 优先提取流程文档状态、运行会话、编辑器分发和结果展示等职责。
2. 保留现有 `FlowEditModel` 的结构编辑能力，避免在新 ViewModel 中再实现一套。
3. 将平台相关编辑器注册移出真正需要复用的编辑模型层，减少不必要的 WinForms 依赖。
4. 对 WPF 逐步采用绑定和命令，不把整个 code-behind 原样搬入一个巨大的 ViewModel。
5. 保留已有主题 Token、专用编辑器和底层 ROI 控件，不为重构而重写。

**验收要点**

增加一个普通工具不需要同步修改多个主窗口分支；运行状态和文档状态有单一来源；结构编辑可以不依赖具体窗口进行调用。

### VF-09：减少内置、插件与双 UI 的重复实现

**现状与影响**

内置与 LDWelding 插件存在图像处理、Region、XLD 和几何工具的相似实现；WPF 与 WinForms 也维护了相近的参数和 ROI 交互逻辑。

重复会增加默认值、输入校验、输出语义和修复结果逐渐分叉的风险。

**关键位置**

`VisionFlow.Tools\Tools\ImageTools.cs`、`RegionTools.cs`、`XldTools.cs`、`GeometryTools.cs`
`VisionFlow.LDWeldingPlugins\LDWeldingImageTools.cs`、`LDWeldingRegionTools.cs`、`LDWeldingXldTools.cs`、`LDWeldingGeometryTools.cs`
`VisionFlow.WpfToolEditors`、`VisionFlow.ToolEditors`、`VisionFlow.Controls`

**修改建议**

1. 先确认重复工具是否存在有意的业务差异，再提取真正一致的算法与参数校验逻辑。
2. 插件保留差异化配置和注册入口，共享底层实现；不要仅因同名就直接删除旧类型。
3. 兼容已保存流程使用的工具身份，重构与 VF-06 的迁移机制配合。
4. 两套 UI 共享参数模型和业务操作，平台相关显示与交互保持各自实现。
5. 明确 WinForms 的维护范围，避免默认所有新交互都必须双份开发。

**验收要点**

共享算法修复能够覆盖对应工具族；有意差异被清楚记录；旧流程不因减少重复代码而失去可加载性。

### VF-10：补齐参数提交、脏标记与未保存变更管理

**现状与影响**

节点、参数和专用编辑器的变更没有统一文档脏状态；预览或参数校验失败后取消编辑，也不应留下对原配置的修改。

当前新建和打开流程前已有通用关闭提示，不能描述为完全没有保护；但它没有区分文档是否修改，也不是完整的保存、放弃、取消交互。

**修改建议**

1. 建立统一变更通知和脏标记，结构与参数修改完成后统一通知文档状态。
2. 保存成功后清除脏标记，失败时保留；新建、打开和关闭按实际脏状态提示。
3. 参数窗口确认时提交一个逻辑变更，取消时不留下非预期修改。
4. 预览结果、日志和选择状态不应被当作文档修改。
5. 模型字节、ROI 和复杂参数使用独立的编辑工作副本；只在确认成功时提交，不保存编辑历史。

**验收要点**

参数取消不会意外改动流程；未保存修改可识别；无修改时不反复提示；保存失败不丢失脏状态和原文件；关闭操作在保存失败时中止。

### VF-11：建立核心回归与真实图像效果基线

**现状与影响**

当前没有自动化测试项目。已有两个示例覆盖基础 Region 和 XLD 流程，但不足以覆盖嵌套分支、引用语义、取消、序列化兼容、插件接入和长期资源行为。

工具存在、流程能够执行，不等于算法在现场图像上已经达到精度与稳定性要求。

**修改建议**

1. 优先覆盖 VF-01、VF-02、VF-03 和 VF-05 的确定性行为，将已确认问题固化为回归用例。
2. 核心流程用不执行 HALCON 算子的简单工具覆盖，尽量降低对本机授权和实际图像的依赖。
3. 单独建立真实图像回归集，保存预期结果、容差、参数版本和失败样本。
4. 为定位与跟随测量增加完整示例，而不只分别展示独立算子。
5. 在固定图像、参数、HALCON 版本和运行环境下记录耗时及资源基线，再决定是否引入模型缓存或其他优化。
6. 涉及 HALCON 的自动化环境，应明确托管 DLL、原生运行库及授权前提，不将环境缺失误判为算法回归。

**验收要点**

核心语义修改能够自动发现回归；真实图像结果有明确预期与容差；性能对比条件一致；新增工具至少覆盖正常输入、异常输入及空结果行为。

## 4. 建议实施顺序

| 阶段 | 重点工作 | 完成标志 |
|---|---|---|
| 第一阶段：正确性 | VF-01、VF-02、VF-03，并同步增加对应回归用例 | 合法引用不误拒绝，非法跨分支引用被阻止，运行配置不漂移，定位失效不产生固定位置结果 |
| 第二阶段：运行与集成契约 | VF-04、VF-05、VF-06、VF-07 | 资源和结果有效期明确，自定义输入可用，旧流程有兼容路径，插件编辑器实际可达 |
| 第三阶段：维护与体验 | VF-08、VF-09、VF-10，持续推进 VF-11 | 新工具接入更集中，重复逻辑减少，取消与保存失败不丢失配置，真实图像效果可持续比较 |

实施时优先采用局部、可回退的改动，不将上述事项合并成一次大规模框架重写。每项修复同时维护其影响到的运行时、序列化、引用元数据和编辑界面，避免只修复其中一个入口。
